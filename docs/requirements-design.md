# 骑有此里 · 产品需求与当前能力

> 状态：当前产品基线，与 `main` 同步维护
>
> 更新时间：2026-10-08

## 1. 产品目标

“骑有此里”服务单个骑行俱乐部，把活动发布、路线说明、骑手资料、Strava 能力数据、报名审批、签到和个人骑行名片放进同一个微信小程序，减少微信群接龙和人工核对。小程序内使用简称“此里”。

本文件描述用户可见行为和产品边界。字段、索引、并发和安全实现以 [CloudBase 数据契约](cloudbase-schema.md) 为准；真实环境是否可用以 [P0 真实报名旅程](verification/p0-real-registration-journey.md) 的现场证据为准。

## 2. 角色与权限

| 角色       | 身份来源                                    | 当前权限                                                                          |
| ---------- | ------------------------------------------- | --------------------------------------------------------------------------------- |
| 骑手       | CloudBase `WXContext.OPENID`                | 浏览活动、维护本人资料和照片、绑定 Strava、报名、查看凭证、取消报名、查看骑行名片 |
| 活动发起人 | 已登录用户，活动 `created_by` 由服务端写入  | 创建和编辑本人草稿、发布/下架，以及从本人的历史活动复制草稿                       |
| 管理员     | `admins` 白名单，服务端按可信 `OPENID` 查询 | 管理并结束全部活动、查看报名、通过/驳回、签到                                     |

客户端传入的 `openid`、角色或本地缓存都不能授予权限。管理员白名单目前通过 CloudBase 控制台维护，没有管理界面。

## 3. 核心用户旅程

### 3.1 活动发布

1. 发起人创建草稿，填写标题、图集、说明、行程节点、集合地点、路线、费用、装备、时间和容量。
2. 管理员可粘贴本人 Strava 路线 URL，服务端读取路线概览、海拔曲线和热门爬坡；活动详情可导出对应 GPX。普通发起人当前不能同步 Strava 路线。
3. 发布只表示公开展示；发布前服务端校验标题、活动起止时间和路线起终点。容量、集合方式分仓、司机、报名截止时间或费用尚未补齐时，活动仍可作为预告展示，但报名保持关闭。
4. 发起人可把本人已发布活动下架回草稿；管理员可结束活动，结束后为终态。本人历史活动可复制成新草稿，但必须重新填写日期。
5. 骑手只能在活动列表看到已发布活动；详情展示图集、路线、集合信息、报名状态和公开的已报名骑手卡片。

活动状态机：

```text
draft <-> published -> finished
```

`status=published` 与“允许报名”是两件事。服务端根据活动时间、截止时间、总容量、分仓容量、费用和必要司机信息计算内部报名判定；只有 `registration_state=open` 才能提交报名。配置不完整时，公开 DTO 使用 `registration_setup_pending=true`、`registration_state=closed` 和 `closed_reason=unavailable`，客户端据此显示“报名待开放”；报名提交接口则以 `SIGNUP_INFO_INCOMPLETE` 拒绝写入。后续补齐配置后自然转为可报名，无需增加活动状态。

### 3.2 资料与 Strava

1. 用户进入“我的”后完成微信云身份验证。
2. 用户维护昵称、真实姓名、手机号、性别、紧急联系人、头像和多张个人照片。
3. 手机号可来自微信动态授权，也可由个人主体手填；前者标记为 `wechat/verified`，后者标记为 `manual/unverified`。当前两者均满足报名门禁，审批页必须展示来源。
4. 用户通过 OAuth 绑定 Strava。授权凭据只在云函数保存，客户端只取得连接状态和统计结果。
5. 系统同步 Strava 累计骑行次数、里程、移动时间和爬升，并生成最近 90 天里程、次数、最长距离、爬升、加权均速和最近活动时间。
6. 个人页与骑行名片在云端数据暂不可用时可以先展示安全缓存，但不能把缓存当作新的服务端事实。

Strava 报名资格的唯一事实源是 `strava_credentials + strava_snapshots`；`profiles.strava` 仅为兼容展示缓存。累计指标来自 Athlete Stats，近期指标使用 90 天活动窗口。快照新鲜度为 24 小时，同步租约为 2 分钟；每页 200 条、最多 5 页，第 5 页仍满 200 条时标记 `coverage_complete=false`。完整空窗口可以显示 0，未知或不完整指标必须显示为空，不能伪造为 0。

### 3.3 报名、审批与签到

1. 骑手从已发布活动进入报名页；资料、活动状态、截止时间、分类名额和 Strava 就绪状态均由服务端复核。
2. 骑手选择自行前往或乘后援车、骑行经验并填写备注，提交后进入 `pending`。
3. 管理员在审批详情查看脱敏资料、手机号来源、骑行照片和 Strava 90 天快照，决定通过或驳回；驳回必须填写理由。
4. `approved` 报名生成凭证。管理员可将其标记为 `checked_in`，重复签到幂等。
5. 骑手可取消 `pending` 或 `approved` 报名；`rejected` 或 `cancelled` 可沿用同一报名记录重新提交。

报名状态机：

```text
pending -> approved -> checked_in
pending -> rejected
pending|approved -> cancelled
rejected|cancelled -> pending
```

`pending + approved + checked_in` 占用活动及集合方式名额；驳回或取消释放名额。状态、容量和审计记录在同一服务端事务中更新。

### 3.4 审批通知

报名按钮在用户手势中请求审核结果订阅授权，拒绝订阅不阻断报名。审批事务写入 Outbox，由定时 worker 发送通过/驳回通知。发送状态带租约、尝试次数和退避；外部结果不明确时进入 `delivery_unknown`，不会自动重复调用微信接口。

### 3.5 公开骑手卡片边界

长期契约是：公开卡片只允许昵称、称号、头像和非敏感骑行指标；不得包含真实姓名、电话、紧急联系人、报名备注、`openid`、token、原始文件 ID 或审计数据。公开图片还必须经过 owner/status/current-reference 校验，并只签发 canonical 媒体的临时 URL。

新设置头像会同步写入 `avatar_visibility=public` 及当前 revision，用于兼容历史客户端和数据。活动详情不再以历史可见性字段作为展示门槛；只在媒体 registry 的 owner、状态、source/origin、canonical 路径和内容元数据完整匹配时签发临时地址。非法来源、脏 registry、缺失媒体或签名失败均隐藏头像且不拖垮活动详情。代码与离线测试不代表目标环境已部署，仍需核对实际云函数版本。

## 4. 页面与功能清单

### 骑手端

- 活动列表：报名中、已满、已截止和已结束状态。
- 活动详情：图集、时间、路线、集合地点、费用、装备、公开报名成员、报名 CTA。
- 报名表单：资料与 Strava 就绪检查、集合方式、经验和备注。
- 行程：本人报名历史和状态。
- 凭证：通过状态、集合信息和签到状态。
- 我的：身份状态、资料完整度、累计与近 90 天骑行名片、资料/头像/相册、Strava 入口和活动管理入口。
- Strava：授权、自动就绪、同步、解绑和错误恢复。

### 活动发起人与管理员端

- 我的活动：本人活动；管理员可查看全部活动。
- 活动编辑：草稿、图集、结构化时间、地点、路线、分组容量、发布/下架/结束。
- 历史复制：把已结束活动复制为新草稿，清空旧媒体和路线所有权数据并重填时间。
- 审批列表与详情：管理员筛选报名，查看脱敏快照，通过/驳回并签到。

## 5. 数据与安全边界

- 所有业务集合客户端读写均拒绝，仅云函数访问；公开活动也由 `activity-read` 返回经过筛选的字段。
- 真实姓名、手机号和紧急电话使用 AES-256-GCM 加密；接口只返回业务所需的脱敏值。
- 不采集或返回证件类型、证件号；存量证件密文只读保留且不解密。
- Strava access/refresh token 加密保存，不进入客户端响应、日志、测试夹具或证据文件。
- 个人媒体先写 owner-bound staging 路径，再由服务端校验真实类型、大小和摘要并复制到 canonical 路径；个人和管理员名片只签发当前有效 canonical 媒体的临时 URL。
- 媒体回收、通知发送、Strava 同步和活动容量均使用租约、幂等键或事务处理并发与未知结果。
- 任何真实 `openid`、手机号、OAuth 参数、token、密钥、密文和原始现场证据都不得提交仓库。

具体集合、索引、状态字段和错误码见 [CloudBase 数据契约](cloudbase-schema.md)。

## 6. 当前限制与后续候选

以下能力当前没有完整后端或用户流程，界面不得伪造成功：

- Strava 豁免申请、授予和撤销。
- 管理员白名单的超管维护界面。
- 在线支付、退款或押金。
- 报名名单 Excel/CSV 导出。
- 多俱乐部、多组织租户与独立 Web 管理后台。

现场签到复用管理员对已通过报名的 `approved -> checked_in` 确认操作。参与者凭证页绘制真实 Code 128 可扫描条码（只承载报名 ID），管理员使用 `wx.scanCode` 解析后进入既有审核详情完成二次确认；不伪装普通文本为二维码。离线核销和批量签到不在本期范围。

## 7. 验收口径

- 本地提交至少通过 `npm run validate`；涉及覆盖率或依赖时再运行 `npm run coverage` 和 `npm run audit:all`。
- CloudBase 资源以 `npm run cloudbase:plan`、人工审核后的 `cloudbase:apply` 和 `cloudbase:verify` 为准，不能从仓库声明推断远端已部署。
- OAuth、手机号授权、媒体权限、订阅消息和完整报名旅程必须在隔离测试环境或真机验证。
- 没有真实执行证据时写“未执行”或“待验证”，不能写成“通过”。
