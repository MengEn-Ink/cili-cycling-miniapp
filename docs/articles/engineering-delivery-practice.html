CILI ENGINEERING CONTROL PLANE

把一次交付，变成可重复的系统

人负责判断，Skills 负责记住规则，Engineering Harness 负责统一执行，GitHub Actions 负责留下云端证据。每一层都只做自己能证明的事。

领域 SkillsHarness Schema v2同提交断点续跑GitHub Actions范围化部署
LAYER 01

Skills

固化项目语境、发布边界和验收清单，避免每次重新解释规则。

LAYER 02

Harness

把已有 npm scripts 组织成统一入口、预检、结果分类与版本化报告。

LAYER 03

Actions

在 PR、main 与发布阶段执行同一套任务，并保存可下载的运行证据。

先给结论

  1. 工程化不是把脚本堆进 CI，而是让规则、执行和证据分别有唯一事实源。
  2. Harness 不重写测试；它只声明任务、检查环境、顺序执行，并生成绑定 commit SHA 的 JSON 报告。
  3. --resume 只接受同一提交、同一配置和同一 schema 的旧报告，已通过任务可跳过，失败任务必须重跑。
  4. Pages、CloudBase、微信开发版各有独立发布边界；文档改动不能误触产品部署。
01

三层控制面：记住、执行、证明

此里的工程控制面刻意分层。Skills 是协作知识，不进入小程序运行时；Harness 是仓库内的执行协议，不接管业务测试实现；Actions 是云端执行者，不重新定义本地质量标准。

记住领域 Skillscili-sandbox-delivery 固化沙箱交付与部署边界；cili-document-harness 固化 Pages 文档结构、契约和线上验收；MR 闭环 Skill 固化单提交、评审和 checks 门禁。
执行Engineering Harnessscripts/harness-registry.mjs 是任务注册表，scripts/harness.mjs 提供 list、preflight、run 与 resume。
证明GitHub ActionsPR 执行 affected，main 并行执行 validate、coverage、audit；每个阶段上传 Harness JSON Artifact。
边界很重要：Skills 是辅助开发的能力层，不是产品依赖；文章只描述公开的工程职责，不把助理环境、凭证或内部实现写进仓库。
02

Harness：统一入口，不制造第二套测试

注册表把稳定 npm scripts 声明为任务：validate、coverage、audit、cloud-install、affected 和 devtools-e2e。配置只表达顺序：verify 是 validate + coverage，release 再加 audit。

# 看清有哪些任务与配置
npm run harness -- list

# 只检查 Node、依赖、环境变量和平台能力
npm run harness -- preflight verify

# 日常验证 / 上线门禁
npm run harness:verify
npm run harness:release

# 修复失败后，只续跑同一提交中尚未通过的任务
npm run harness -- run release --resume

报告是机器契约，不是漂亮日志

passed任务完成且退出码为 0。
failed任务已执行，代码或测试失败。
blocked环境、依赖、平台或凭证条件不满足。
skipped同一提交的历史报告已证明该任务通过。

Schema v2 在顶层记录 commitSha、mode、outcome、failureCategory 与 resumedFrom；任务级记录状态、时间、退出码、失败类别和跳过原因。旧 SHA、旧 schema 或不同配置的报告会被拒绝，防止把历史成功冒充当前成功。

04

GitHub Actions：同一任务，三种时间窗口

Pull Requestaffected-pr 根据 Git Diff 选择验证范围，未知路径、公共层或高风险改动回退全量；报告无论成功失败都上传。
main pushvalidate、coverage、audit 三个 job 并行，每个 job 独立安装依赖、执行 Harness、上传独立报告。
Nightly每天全量检查全局不变量；确定性格式问题可进入受限修复流程，业务与安全问题只报告、不猜测修复。

Artifact 名称带 PR 号或 GitHub run id，保留 14 天。它解决的是“失败时还能读到结构化上下文”；本轮不在 Harness 内调用 GitHub API 自动下载历史 Artifact，避免把鉴权和平台耦合塞进本地执行器。

部署不是一个按钮，而是范围判断

目标触发与范围成功信号

CloudBaseCI 成功后按上次成功基线计算函数、索引和规则影响范围目标函数 Active、环境配置一致、相关 smoke 通过
体验版 / UAT人工触发 candidate → verified 两阶段晋级公众平台回读、真机旅程和不可变发布清单一致
本项目的发布原则：沙箱负责代码修改和本地验证；合并后的部署、上传与正式 Pages 发布统一由 GitHub Actions 执行并核验。范围决策为“无需部署”也是有效结果，但必须有可追溯证据。
06

失败恢复：只复用仍然成立的证据

长流程失败后，最危险的做法是“看起来刚才通过过”就手工跳过。Harness 的恢复规则更严格：只有 schema、selection 和 commit SHA 全部一致，才把旧报告里的 passed 任务标为 skipped；失败、未执行和阻塞任务仍会执行。

允许复用

同一提交、同一 profile、同一 schema；报告明确记录任务已通过，并保留来源路径与完成时间。

拒绝复用

代码已经改变、profile 不同、报告格式升级、报告不存在或状态不是 passed。此时必须重新生成证据。

失败分类也分层：预检问题归为 environment，进程无法启动归为 infrastructure，测试或审计非零退出归为 application，中断后留下 pending 归为 incomplete。分类帮助定位，不改变“未通过就是不能合并”的门禁。

07

真正跑通项目的检查点

检查点通过定义
规则唯一Skill 解释协作边界，registry 声明执行任务，workflow 只负责调用，不复制任务清单。
本地可复现新环境执行 npm ci、cloud:install、Harness preflight 后能得到明确 passed / failed / blocked。
版本可信所有报告绑定当前 commit SHA；跨版本续跑被拒绝。
云端可诊断PR 和 main 的 Harness Artifact 在失败时仍可下载，且包含失败类别与任务状态。
发布不越界Pages-only 变更只发布 Pages；产品或云端变更由 decision 脚本确定部署范围。
线上有回读checks 全绿只是前提；正式 URL、微信版本、CloudBase 状态按变更范围逐项复验。
