## 2. 通知功能：从“用户结果通知”补齐到“双向状态通知”

### 2.1 当前能力

- 报名审批结果通过 `notification_outbox` 异步发送，已有租约、重试退避和未知结果保护。
- 候补进入、候补转正及部分活动变化已有通知任务。
- 用户提交报名进入 `pending` 时，管理员目前不会收到新待办提醒。
- 用户取消报名时，管理员目前也不会收到提醒。

### 2.2 推荐方案

通知分成两层，避免把微信订阅消息当成唯一可靠入口：

1. **站内管理待办为必达层**：提交或取消报名时，在服务端事务内写入可查询的管理员待办/事件；管理页展示未处理数量和更新时间。
2. **微信订阅消息为增强层**：管理员在管理页主动订阅“新报名待处理”等模板；只有取得订阅授权时才发送，拒绝授权不影响业务状态。
3. **统一复用 Outbox**：所有外部通知继续使用幂等键、租约和退避；业务事务只写事件，不同步调用微信接口。
4. **收件人按事件确定**：管理员事件发给启用的管理员；用户事件只发给对应报名用户；活动变更只通知受影响的 `pending/approved/checked_in` 用户。

### 2.3 推荐通知矩阵

| 事件 | 收件人 | 站内待办 | 微信订阅消息 | 本期建议 |
| --- | --- | --- | --- | --- |
| 新报名进入 `pending` | 启用的管理员 | 必须 | 管理员已订阅时发送 | V1 |
| 用户取消 `pending/approved` | 启用的管理员 | 必须 | 可选，建议聚合防刷屏 | V1 |
| 审批通过/驳回 | 报名用户 | 状态可见 | 沿用现有实现 | 已有，补完整回归 |
| 候补进入/转正 | 报名用户 | 状态可见 | 沿用现有实现 | 已有，补完整回归 |
| 活动时间、集合点或状态发生关键变化 | 受影响报名用户 | 必须可追溯 | 已订阅时发送 | V2 |
| 活动结束 | 已通过/已签到用户 | 非待办，仅时间线记录 | 默认不发，避免低价值打扰 | 暂不做 |

### 2.4 验收口径

- 用户提交报名后，所有启用管理员都能在管理入口看到同一条新待办；重复提交或重试不产生重复事件。
- 管理员未订阅微信消息时，站内待办仍然存在；已订阅时可收到一次消息。
- 用户取消后待办正确更新，不再保留“待审批”的错误角标。
- 审批结果、候补、活动关键变化分别验证正常、重复消费、发送失败和 `delivery_unknown`。

## 3. 新用户创建活动：采用“申请成为发起人”

### 3.1 当前能力与风险

当前角色实际上是三种业务身份：骑手、活动发起人和管理员。活动 `created_by` 由服务端写入，但任何已登录用户都可以创建本人草稿并发布/下架本人活动；管理员白名单只控制跨活动管理、审批和结束活动。

这意味着“创建活动能力”当前不是审批授予的权限。直接复用 `admins` 白名单会把“可以发起活动”和“可以管理所有活动/审批报名”绑在一起，权限过大，不推荐。

### 3.2 推荐角色模型

| 角色 | 权限 |
| --- | --- |
| `member` | 浏览、维护资料、报名、查看本人凭证 |
| `organizer` | 创建、编辑、发布/下架本人活动，管理本人模板；不能审批他人活动报名，除非后续单独授权 |
| `admin` | 审核发起人申请、管理全部活动、审批报名、签到 |

新增 `organizer_applications` 申请记录，建议状态为 `pending -> approved/rejected`；同一用户只允许存在一条进行中的申请。客户端不得直接写角色或管理员集合，审批必须由云函数校验可信 `OPENID` 后完成。

### 3.3 推荐产品流程

1. 普通用户点击“创建活动”时，如果没有 `organizer` 权限，进入申请页。
2. 申请填写发起理由、常用活动类型、联系方式和安全承诺；提交后显示审核状态。
3. 管理员收到站内待办，审批通过后授予 `organizer`。
4. `organizer` 仅管理本人活动；管理员保留全局管理能力。
5. 权限被停用后，不再允许创建或发布；既有活动保留并由管理员接管，避免直接删除数据。

### 3.4 存量兼容

- 已创建过活动的非管理员用户不能直接失权。上线前根据 `activities.created_by` 生成待确认名单，由管理员批量确认为发起人，或在一段迁移期内按既有活动所有权保留权限。
- 服务端必须同时校验角色与活动所有权，不能只依赖前端隐藏入口。

### 3.5 验收口径

覆盖未申请、待审核、驳回、通过、停用、本人活动、他人活动和管理员全局管理；角色缓存过期后仍以服务端事实为准。

## 4. 活动标签与模板

### 4.1 当前能力

“复制历史活动”已经能把本人既有活动复制成新草稿，是模板能力的可复用基础；当前没有独立模板集合，也没有稳定的 `tags/category` 数据契约。

### 4.2 推荐分期

#### V1：受控标签

- `tags` 使用服务端白名单枚举，例如：`新手友好`、`公路`、`山地`、`长距离`、`爬坡`、`夜骑`。
- 编辑页支持多选，列表和详情展示标签；首期不做复杂组合筛选，避免先引入索引成本。
- 标签只描述活动特征，不代替报名资格、难度、路线类型等已有结构化字段。

#### V2：模板库

- 新建独立 `activity_templates`，区分“我的模板”和管理员维护的“公共模板”。
- 模板保存稳定配置：标题建议、说明、集合方式、装备、费用、容量结构、标签等。
- 套用时必须清空日期、活动状态、报名记录、凭证、签到、审计信息，以及不能跨所有者复用的媒体/路线所有权数据。
- 支持从活动“保存为模板”、从模板创建草稿、重命名、复制和删除本人模板；公共模板只允许管理员维护。

### 4.3 为什么不直接把历史活动当模板

历史活动包含过期日期、状态、报名数据和媒体所有权语义；继续堆叠“复制活动”分支会让安全边界越来越难验证。独立模板快照能明确哪些字段可复用，并为公共模板提供稳定权限边界。

### 4.4 验收口径

验证标签非法值拒绝、套用模板后敏感字段清空、模板所有权隔离、公共模板只读、存量活动无标签时正常展示。

## 5. 报名凭证与骑行名片图片语义

### 5.1 凭证编号

当前新凭证格式为 `RE-YYYYMMDD-XXXXXX`。推荐改为：

```text
CL-YYYYMMDD-XXXXXX
```

- 只影响新生成凭证；历史 `RE-` 凭证继续有效，不批量改号。
- 扫码和查询入口在兼容期同时接受 `CL-` 与 `RE-`，但只生成 `CL-`。
- 条码仍只承载服务端可验证的报名 ID；展示编号不能成为授权依据。

### 5.2 头像与背景图必须分离

当前模型已将 `avatar_file_id` 与 `background_photo` 分开，骑行名片背景优先使用 `background_photo`，缺失时兼容存量 `photos[0]`，再缺失时使用品牌兜底背景；**不得把头像放大后当作名片背景**。

后续实现需要继续收紧语义：

- 头像只用于头像槽位、报名成员身份和名片人物标识。
- 背景图只用于骑行名片/个人页背景；没有背景图时使用品牌兜底图，不回退头像。
- 新上传路径或媒体元数据显式区分 `avatar` 与 `background`；签名和回收都按用途校验。
- 存量 `photos[0]` 只作为背景兼容来源，不迁入头像字段，也不覆盖用户后来设置的 `background_photo`。

### 5.3 验收口径

- 新凭证显示 `CL-`；旧 `RE-` 条码与详情仍可识别。
- 只上传头像时，名片显示品牌兜底背景而不是头像放大图。
- 只上传背景图时，头像保持独立占位；替换/删除其中一类不会改动另一类。
- 媒体 owner、用途、canonical 路径不匹配时拒绝签名，不以静默互换图片兜底。

## 6. 恢复浅色/暗色双主题

### 6.1 当前能力与截图结论

仓库当前为单一明亮外观：页面主题同步入口已移除，设置页没有外观开关。用户提供的两张参考截图展示的是同一报名页的浅色与深色镜像方案，适合复用以下设计：

- 三格票据式步骤条；
- 同级描边卡片，取消“大卡套小卡”；
- 黑/白/灰为主、橙色只承担关键状态与主要操作；
- 活动摘要卡作为跨主题保持一致的品牌视觉锚点。

不直接照搬深色稿中对比不足的禁用按钮；深色卡片描边必须比页面背景更亮，确保边界可见。截图仅作为方向参考，最终以真机对比度和全页面验收为准。

### 6.2 推荐范围

首期只提供两种手动模式：

- `浅色`：默认值；
- `暗色`：用户在“设置 → 外观”主动切换。

本期不增加“跟随系统”和自定义壁纸，避免同时引入第三种状态与背景可读性问题。这里的“背景切换”定义为页面浅/暗外观切换，不是把个人照片设置为全局壁纸。

### 6.3 实现原则

1. 恢复主题状态与本地持久化，冷启动前尽早应用，避免首屏闪白。
2. 使用语义 Token 管理页面背景、表面、主/次文字、边框、蒙层、禁用态和品牌强调色；禁止页面继续新增主题相关硬编码颜色。
3. TabBar、导航栏、骨架屏、弹窗、Canvas 海报及图片占位分别验收，不能只切换页面底色。
4. 设置页切换即时生效；存储读取失败或旧缓存异常时安全回退浅色。
5. 品牌橙在两种主题中保持同一语义，但分别通过对比度测试。

### 6.4 验收口径

- 设置页可在浅色/暗色之间即时切换，重启后保持选择。
- 375×812 与窄屏下覆盖首页、详情、报名、行程、凭证、个人页、管理页和设置页。
- 正文、辅助文案、描边、输入框、禁用按钮、Toast、TabBar 在两种主题中均清晰可读。
- 切换期间无明显闪白、无旧主题颜色残留；Canvas/分享海报保持既定输出，不被页面主题误改。

## 7. 更新日志改为一句话

### 7.1 推荐展示契约

设置页每个版本只展示：

```text
版本号 · 日期
一句话更新文案
```

一句话建议控制在 18–36 个汉字，写用户感知结果，不罗列实现细节；语气可以滑稽，但不能拿安全、隐私、支付或数据丢失开玩笑。

示例：

- `资料检查终于统一口径了，这次不会门口说能进、报名时又把你拦下。`
- `GPX 现在会把问题说明白，不再只留下一脸无辜的“失败”。`
- `深色模式回来了，夜骑刷小程序终于不用顺便照亮整条街。`

### 7.2 推荐实现

- 页面改为只渲染一句 `copy`（或收敛后的 `summary`），不再展开 `features` 列表。
- 版本号、日期、`latest` 和发布门禁继续保留，保证自动上传与追溯不受影响。
- 旧记录可在展示层兼容，不要求一次性迁移全部历史内容；新版本开始使用一句话契约。

### 7.3 验收口径

- 最新版本只显示一句话，没有折叠的功能明细。
- 文案过长时正常换行，不能挤压版本号或日期。
- `latest: true` 唯一、版本递增和产品改动必须更新日志的门禁继续生效。

## 8. PR 拆分与依赖建议

| PR | 范围 | 依赖 | 是否涉及 CloudBase 部署 |
| --- | --- | --- | --- |
| A | 发起人申请、审批与 `organizer` 权限 | 无，优先 | 是：权限、申请集合与相关云函数 |
| B | 管理员新报名/取消待办与订阅消息 | A 的角色收件人边界 | 是：报名、通知 worker、索引/模板配置 |
| C | 凭证 `CL-` 与媒体用途隔离 | 无，可并行 | 是：registration/profile；小程序同步上传 |
| D | 活动标签 | A 的编辑权限 | 是：活动 schema/索引与小程序 |
| E | 活动模板 | D 标签契约 | 是：模板集合、活动管理云函数与小程序 |
| F | 浅色/暗色主题 + 一句话日志 | 无，可并行 | 否：仅小程序与测试 |

每个功能 PR 都应包含对应的发布日志、自动化测试和独立验收证据；CloudBase 变更必须完成 `plan -> apply -> verify` 与受影响云函数部署后，才能宣称交付完成。

## 9. 本次澄清 PR 的边界

本 PR 只固化已核对的现状、推荐方案、分期、依赖与验收标准，不改变运行时行为，也不提前创建未接线的数据集合或配置。后续按第 8 节拆分实施，避免一个 PR 同时修改权限、通知、活动模型、媒体契约与全站主题。
