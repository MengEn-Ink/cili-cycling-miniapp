# 组织地基与审批权限需求

> 文档状态：待实施需求基线
>
> 适用阶段：小圈子运营期
>
> 更新日期：2026-10-17
>
> 重要说明：本文描述目标规则，不代表当前代码已经实现。

## 1. 背景与目标

当前系统以“已登录用户可以创建并发布活动、全局管理员管理全部活动”为主，适合单一熟人圈的早期使用，但缺少组织申请、资源归属和发布前审核边界。随着俱乐部与用户增加，如果继续沿用全局二元角色，任何用户都可能直接建立组织或公开发布内容，俱乐部管理员也无法只管理自己的组织。

本期目标不是建设面向大规模平台的复杂多租户系统，而是在小圈子范围内建立一套简单、严格、可追溯的组织地基：

1. 所有俱乐部创建申请必须由平台所有者审批。
2. 普通成员的自发活动挂靠俱乐部时，必须由该俱乐部管理员审批后发布；俱乐部有效 `OWNER/ADMIN` 发布本人活动时默认发布并记录审计。
3. 用户自发活动进入公开活动池时，必须由平台所有者审批后发布。
4. 所有审批均由服务端判权并记录审计，客户端不能通过伪造角色、状态或组织 ID 绕过。
5. 规则优先保证可控和可解释，不提前引入多级会签、复杂工作流编排或独立 Web 后台。

## 2. 名词与角色

### 2.1 平台所有者

平台最高管理身份，首期由现有全局管理员白名单中的唯一超级管理员承担。

核心权限：

- 审批或驳回俱乐部创建申请。
- 审批或驳回公开活动发布申请。
- 查看全部俱乐部和活动的审批记录。
- 停用俱乐部、下架活动、撤销违规管理员权限。
- 在俱乐部审批人缺位或存在利益冲突时兜底处理。

### 2.2 俱乐部所有者

俱乐部申请通过后，申请人成为该俱乐部所有者 `OWNER`。所有者负责俱乐部资料、管理员和成员治理，但不能绕过平台所有者创建新的俱乐部。

### 2.3 俱乐部管理员

由俱乐部所有者配置，角色为 `ADMIN`。管理员只能管理所属俱乐部，不能查看或审批其他俱乐部的私域申请。

### 2.4 活动发起人

具备活动创建资格的用户。公开活动可以由普通已登录用户申请发布；俱乐部活动首期仅允许该俱乐部有效成员发起。

### 2.5 普通骑友

可浏览有权限查看的活动、申请加入俱乐部、提交俱乐部创建申请、创建活动草稿并提交审核，但没有任何审批权。

## 3. 资源归属

### 3.1 俱乐部

- 每个俱乐部必须有唯一 `owner_openid`，同时拥有一组成员关系。
- 用户可加入多个俱乐部，成员关系必须使用独立集合表达，不能在用户资料中保存单一 `club_id`。
- 俱乐部申请通过前，不创建可对外使用的正式俱乐部；申请记录与正式资源分开。
- 平台所有者拥有监管权，不自动成为每个俱乐部的日常管理员。

### 3.2 活动

活动发布目标二选一：

| 发布目标 | 资源归属 | 审批人 | 发布后范围 |
| --- | --- | --- | --- |
| 俱乐部活动 | 必须关联一个有效 `club_id` | 普通成员活动由该俱乐部 `OWNER/ADMIN` 审批；管理员本人活动默认发布 | 按活动可见性向成员或公开用户展示 |
| 公开活动 | `club_id` 为空 | 平台所有者 | 进入平台公开活动池 |

MVP 中一个活动最多关联一个俱乐部；公开活动的 `club_id` 为空并统一显示为“此里公开活动”。本期不设计联合主办、协办、跨俱乐部联办或多个组织共同归属，也不引入主俱乐部/首选俱乐部概念。

## 5. 俱乐部申请流程

### 5.1 申请字段

首期仅收集审批真正需要的信息：

- 俱乐部名称、所在城市、简介和封面。
- 申请人及联系方式。
- 加入方式：公开申请、邀请码、管理员邀请。
- 预计成员规模和主要活动类型。
- 俱乐部规则或群规摘要。

名称需要做规范化后的重复检查，但重复名称不自动合并，由平台所有者人工判断。

### 5.2 状态机

```text
draft → pending_review → approved
                     ↘ rejected → draft → pending_review
                     ↘ withdrawn
approved → suspended → approved
approved → closed
```

| 状态 | 含义 | 允许动作 |
| --- | --- | --- |
| `draft` | 申请人编辑中 | 编辑、提交、删除 |
| `pending_review` | 等待平台所有者处理 | 申请人撤回；平台所有者通过或驳回 |
| `approved` | 已创建正式俱乐部 | 配置资料、成员、管理员和活动 |
| `rejected` | 已驳回 | 查看原因、修改后重新提交 |
| `withdrawn` | 申请人已撤回 | 复制为新草稿 |
| `suspended` | 被平台停用 | 禁止新活动、成员变更和公开展示 |
| `closed` | 已关闭 | 只保留必要审计，不可恢复使用 |

### 5.3 审批要求

- 驳回必须填写原因。
- 通过时在同一事务或幂等流程中创建正式俱乐部和 `OWNER` 成员关系。
- 重复点击通过不能创建两个俱乐部。
- 申请内容变更后必须产生新的 `review_version`，历史审批意见只读保留。
- 平台所有者本人提交俱乐部申请也要经过明确的“确认创建”动作并留下审计记录，不允许接口静默直建。

## 6. 活动发布审批流程

### 6.1 状态机

```text
普通成员的俱乐部活动 / 普通用户的公开活动：
draft → pending_review → published → finished
                     ↘ rejected → draft → pending_review
                     ↘ withdrawn → draft

俱乐部 OWNER/ADMIN 在所属俱乐部发起活动：
draft → published（角色校验通过后默认发布并写审计）

published → change_pending → published
published → cancelled
published → taken_down
```

| 状态 | 含义 | 对外可见 |
| --- | --- | --- |
| `draft` | 发起人编辑中 | 否 |
| `pending_review` | 普通发起人的首次发布待审批 | 否 |
| `rejected` | 审批驳回 | 否，仅发起人可见 |
| `withdrawn` | 发起人撤回审核 | 否 |
| `published` | 人工审批通过，或具备权限的俱乐部管理员默认发布 | 按可见性规则 |
| `change_pending` | 普通发起人对已发布活动的关键修改待审批 | 旧版本继续生效 |
| `cancelled` | 发起人或管理员取消 | 是，显示取消原因 |
| `taken_down` | 管理员强制下架 | 否，保留审计 |
| `finished` | 活动已结束 | 是，进入历史活动 |

### 6.2 审批与默认发布路由

服务端根据提交时的发布目标和发起人在目标范围内的实时角色生成不可由客户端修改的路由：

```text
club_id 有值
  → 校验俱乐部处于 active
  → 校验发起人是该俱乐部有效成员
  → 发起人是该俱乐部 OWNER/ADMIN：默认发布
  → 其他成员：进入该俱乐部审批池

club_id 为空
  → 发起人是平台所有者：显式确认后默认发布
  → 其他用户（包括其他俱乐部管理员）：进入平台公开活动审批池
```

普通成员提交审核后保存 `review_scope`、`review_target_id` 和 `review_version`。审批时必须再次校验这些值与当前活动版本一致，避免用户在待审期间换俱乐部或改公开范围后沿用旧审批。

### 6.3 管理员默认发布规则

“管理员默认发布”是服务端基于当前角色执行的受控发布，不是客户端把活动状态直接写成 `published`，也不是生成一条待办后由管理员点击审批自己。

必须同时满足：

1. 活动关联一个有效且未停用的 `club_id`。
2. 发起人在该俱乐部的实时成员关系为有效 `OWNER` 或 `ADMIN`。
3. 活动必填字段、时间、路线、容量和安全规则校验通过。
4. 发布目标仍是该俱乐部；改成公开活动时必须重新进入平台所有者审批路由。
5. 当前版本没有已生效的取消、下架或并发审批终态。

服务端发布时写入：

- `approval_mode = role_auto_publish`。
- `approved_by = created_by`，同时记录角色快照 `approved_role = OWNER/ADMIN`。
- `review_scope = club`、`review_target_id = club_id` 和当前 `review_version`。
- `published_at`、服务端时间、请求幂等键与审计记录。

边界规则：

- 俱乐部管理员身份只对所属俱乐部有效，不能让其公开活动或其他俱乐部活动自动发布。
- 管理员从草稿点击“发布”时，界面明确提示“将以俱乐部管理员身份直接发布”，不能仍显示“提交审核”。
- 管理员可继续“保存草稿”，默认发布只发生在其主动点击发布且校验通过时。
- 管理员角色在请求到达服务端前被移除时，按普通成员重新路由到审批池，不允许使用旧缓存自动发布。
- 网络重试或重复点击必须复用同一幂等结果，不能生成重复活动、重复通知或重复审计。
- 默认发布后仍可被其他俱乐部管理员或平台所有者下架；下架后再次发布必须重新执行完整权限和内容校验。

### 6.4 关键修改重审与管理员直发

普通成员发起的活动修改以下字段时，不直接覆盖线上版本，而是产生待审版本：

- 发布目标、所属俱乐部、公开或私域可见范围。
- 标题、日期、集合时间、集合地点。
- 路线、距离、爬升和难度。
- 费用、人数、报名截止和后援车能力。
- 领队、收队、司机、紧急联系人和安全说明。

管理员修改本人在所属俱乐部发起的活动时，若活动仍归属同一俱乐部且管理员角色仍有效，关键修改也可以默认发布为新版本；服务端必须原子替换当前发布版本，并记录 `role_auto_publish` 审计。所属俱乐部、发布范围改为公开或俱乐部已停用时，不适用默认发布。

非关键修改，例如错别字修正或不改变含义的图片替换，可以由有权限的管理员直接更新，但仍记录审计。首期若难以可靠区分，普通成员的活动宁可全部重审，不做客户端特判。

### 6.5 审批结果

- 通过：发布对应 `review_version`，写入审批人、时间和意见。
- 驳回：必须填写原因，活动回到发起人可编辑状态。
- 撤回：只允许发起人在审批完成前操作。
- 重提：生成新版本，审批人能看到上次驳回原因与本次变更摘要。
- 并发审批：第一个合法终态生效，其他审批请求返回“该版本已处理”，不得覆盖结果。

## 7. 小圈子阶段的推荐默认规则

以下规则按“收紧权限、降低运营复杂度”作为小圈子阶段默认：

1. **非成员不能向俱乐部投稿活动**：先加入俱乐部，再申请发布。
2. **普通成员活动单人审批即可**：任一有效 `OWNER/ADMIN` 通过即发布，不做多人会签。
3. **俱乐部管理员本人活动默认发布**：有效 `OWNER/ADMIN` 在所属俱乐部点击发布后，服务端校验并直接进入 `published`，不生成自审待办，同时写完整审批审计。
4. **平台所有者发起公开活动**：执行显式“确认并发布”，不进入自己的待办列表，但必须记录等价审批审计。
5. **不设置超时自动通过或自动驳回**：只展示待办时长并发送提醒，避免系统替人做发布决策。
6. **审批权不向普通成员委托**：MVP 只使用固定角色，不建设自定义权限编辑器。
7. **平台所有者不介入正常俱乐部审批**：只有无可用审批人、俱乐部停用、投诉或违规处理时才兜底。

## 8. 俱乐部异常与退出边界

### 8.1 管理员变更

- `OWNER` 可以新增或移除 `ADMIN`。
- 不能移除最后一名可用管理员。
- `OWNER` 退出或注销前必须先完成所有权移交。
- 被移除的管理员立即失去待办访问权；已经完成的审批记录保留原审批人快照。

### 8.2 俱乐部停用

平台所有者停用俱乐部时：

- 禁止创建、提交和审批新的俱乐部活动。
- 所有未处理的活动申请标记为 `blocked`，不得自动驳回或丢失。
- 已发布的未来活动进入待处置列表，由平台所有者选择取消、转公开重审或恢复俱乐部后继续。
- 历史活动、报名和审计记录保留；客户端不得把停用伪装成资源不存在。

### 8.3 展示、快照与退出边界

- 活动列表与活动详情优先展示当前有效俱乐部资料；当前资料缺失、俱乐部停用/关闭或不可读时，回退到该活动的发布快照，并以中性小标签标注“历史归属”。
- “我的行程”和“报名凭证”只使用发布/成行时固化的活动归属快照，不依赖当前成员关系或俱乐部当前名称；快照必须按 `activity_id` / `credential_id` 查找，不能使用固定记录属性名。
- 用户退会后，个人中心立即停止展示该成员关系；历史行程、凭证、报名与审计仍保留原活动归属快照，并标注“历史归属”。
- 俱乐部停用或关闭后，不再作为有效成员关系出现在个人中心；历史活动、行程和凭证继续可读，不伪装为资源不存在。
- 个人中心只展示 `active` 成员关系。单俱乐部显示头像、名称与本人角色；多俱乐部最多显示 4 个头像，超出显示 `+N`；无有效关系显示中性空态。
- 用户可加入多个俱乐部，但不设置主俱乐部或首选俱乐部。
- 公开活动及任何无法解析组织归属的兼容数据统一中性兜底为“此里公开活动”，渲染不得抛错。

### 8.4 活动转移

- 待审核活动不能直接从 A 俱乐部改到 B 俱乐部；发起人必须撤回后重新提交。
- 已发布活动不能直接改变俱乐部归属；MVP 采用“复制为新草稿 + 原活动取消”的方式。
- 公开活动转俱乐部活动或反向转换均视为新审批范围，必须重审。

## 9. 通知与待办

### 9.1 通知对象

| 事件 | 接收人 |
| --- | --- |
| 新俱乐部申请 | 平台所有者 |
| 俱乐部申请通过/驳回 | 申请人 |
| 新俱乐部活动待审 | 该俱乐部有效 `OWNER/ADMIN` |
| 管理员本人活动默认发布 | 发起管理员收到发布结果；按俱乐部通知偏好触发新活动提醒，不生成审批待办 |
| 新公开活动待审 | 平台所有者 |
| 活动通过/驳回 | 发起人 |
| 已发布活动关键变更通过 | 已报名用户和受影响管理人员 |
| 俱乐部停用或活动下架 | 发起人、相关管理员和已报名用户 |

### 9.2 通知原则

- 站内待办是事实源，微信订阅消息是提醒，不是审批结果的唯一载体。
- 通知失败不能回滚已经成功的审批，但必须进入可重试 Outbox。
- 多名管理员只生成一条业务待办，多端提醒可以扇出；其中一人处理后其他人的待办同步结束。
- 通知内容只放必要信息，不包含完整手机号、紧急联系人或其他敏感资料。

## 10. 审计与安全

每次审批与权限变化至少记录：

- `actor_openid`：操作人可信身份。
- `action`：提交、撤回、通过、驳回、停用、恢复、下架等。
- `target_type/target_id`：俱乐部申请、俱乐部、活动版本或成员关系。
- `before_status/after_status`。
- `review_version`、`approval_mode`、审批角色快照和请求幂等键。
- `reason`：驳回、停用和下架必填。
- `created_at`、可信服务端时间与必要请求追踪 ID。

安全不变量：

1. 所有业务集合客户端读写继续拒绝，仅云函数访问。
2. 审批接口只接受业务目标和操作意图，不接受客户端声明的审批人角色。
3. A 俱乐部管理员无法枚举、读取或处理 B 俱乐部私域申请。
4. 审批或默认发布权限在动作发生时实时校验，不能只依赖待办生成时的旧角色或客户端缓存。
5. `role_auto_publish` 只能用于发起人在目标俱乐部拥有有效 `OWNER/ADMIN` 角色的本人活动，不能扩展到公开活动或其他俱乐部。
6. 同一 `review_version` 只能有一个终态结果。
7. 已驳回、撤回或被他人处理的版本不能再次通过。
8. 审批日志不得记录手机号、体重、FTP、紧急联系人等原始敏感值。

## 11. MVP 页面与功能清单

### 用户侧

- 我的俱乐部申请：草稿、待审核、已通过、已驳回。
- 创建俱乐部申请与驳回后修改重提。
- 活动编辑页选择“俱乐部活动 / 公开活动”。
- 提交前根据实时角色显示准确结果：普通成员显示“提交俱乐部审核”，俱乐部 `OWNER/ADMIN` 显示“发布后立即上线”，公开活动显示“提交平台审核”。
- 我的活动显示待审核、默认发布、驳回原因、撤回与重新提交等状态。

### 俱乐部管理侧

- 俱乐部活动审批列表和详情。
- 通过、驳回、查看版本差异，并区分人工审批与 `role_auto_publish` 审计记录。
- 管理员发布本人活动时显示直接发布结果，不生成待审批卡片。
- 成员与管理员列表。
- 管理员配置与最后管理员保护。

### 平台所有者侧

- 俱乐部申请审批列表和详情。
- 公开活动审批列表和详情。
- 无审批人俱乐部活动的兜底队列。
- 俱乐部停用、恢复和活动下架入口。
- 按目标、操作人和时间查询审计记录。

## 12. MVP 验收标准

### 俱乐部申请

- 未经平台所有者通过，申请人无法获得正式俱乐部或 `OWNER` 权限。
- 重复通过请求不会创建重复俱乐部或重复成员关系。
- 驳回必须有原因，申请人修改后可以提交新版本。

### 俱乐部活动

- 非成员不能提交俱乐部活动。
- A 俱乐部管理员看不到 B 俱乐部待审活动。
- 普通成员活动在审批通过前，不出现在成员或公开活动列表中。
- 有效 `OWNER/ADMIN` 发布本人在所属俱乐部的活动时直接进入 `published`，不生成待审记录，并写入 `role_auto_publish` 审计。
- 管理员身份失效、俱乐部停用、目标俱乐部不匹配或改为公开活动时，不能走默认发布。
- 管理员重复点击或网络重试只产生一个发布版本、一组通知和一条幂等审计结果。

### 公开活动

- 普通用户提交后进入平台所有者待办，不能绕过审批直接改成 `published`。
- 平台所有者通过后才进入公开列表。
- 驳回、撤回和版本过期请求均不能发布。

### 变更与异常

- 普通成员已发布活动的关键修改不会直接覆盖当前线上版本；管理员本人在所属俱乐部活动的关键修改可按默认发布规则原子切换版本。
- 俱乐部停用后不能产生新的活动审批或管理员默认发布，存量未来活动进入待处置队列。
- 并发审批只有一个结果生效，所有动作均可从审计记录追溯。

## 13. 分期建议

### M0：审批地基

- 平台所有者身份和服务端权限守卫。
- 俱乐部申请状态机与审批。
- 活动草稿、提交、管理员默认发布、驳回、撤回、通过与审批路由。
- 待办、通知和审计最小闭环。

### M1：俱乐部治理

- 成员加入、退出、邀请和管理员配置。
- 俱乐部私域/公开展示及报名范围。
- 俱乐部停用、恢复和无审批人兜底。

### M2：发布质量

- 已发布活动关键修改版本和差异查看。
- 审批时长、驳回原因和重复修改分析。
- 发起人信用、举报与违规处置。

## 14. 已确认决策与待讨论项

### 14.1 已确认

- 俱乐部有效 `OWNER/ADMIN` 可以发布本人在所属俱乐部发起的活动，服务端校验通过后默认进入 `published`。
- 默认发布不生成自审待办，但必须写入与人工审批等价的角色、版本、幂等和审计信息。
- 该权限不扩展到公开活动、其他俱乐部活动、停用俱乐部或已失效管理员。

### 14.2 待讨论

以下问题不阻塞需求文档形成，但实施前需要最终拍板：

1. **非成员能否向俱乐部投稿活动？**
   - 推荐：MVP 不能，先加入俱乐部。
2. **普通成员的俱乐部活动需要几名管理员通过？**
   - 推荐：一名即可，符合小圈子阶段；不建设多人会签。
3. **平台所有者自己发起公开活动如何处理？**
   - 推荐：显式确认后直接发布并记录审计，不制造自己审批自己的待办。
4. **待审核多久后自动处理？**
   - 推荐：永不自动通过或驳回，只提醒待办时长。
5. **俱乐部停用时未来活动如何处理？**
   - 推荐：先冻结为待处置，不批量自动取消，避免误伤已报名活动。

## 15. 与现有系统的关系

当前代码中的 `admins` 白名单、活动 `created_by`、报名审核和审计能力可以作为实现参考，但不能直接等同于本文目标：

- 当前全局 `admin/member` 二元角色需要扩展为平台角色和俱乐部成员角色两层。
- 当前 `draft/published/finished` 活动状态需要增加发布审批版本，且不能与报名审批状态混用。
- 当前活动内 `team_id/team_name` 只表示单次活动分组，不能复用为俱乐部。
- 当前 Pages 中的角色与业务规则仍描述已实现基线；本文以“待实施需求基线”独立展示，避免把规划写成上线事实。
