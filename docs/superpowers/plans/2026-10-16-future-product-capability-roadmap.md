# 此里骑行小程序未来产品能力路线图

> 状态：产品调研与分期建议，不代表已实现或已上线
>
> 基线：`origin/main` @ `731489a`（2026-10-17）
>
> 目标：从“单俱乐部活动工具”演进为支持多俱乐部、日常活动与精品局协作的骑行活动平台。

## 1. 调研结论

当前系统已经具备活动创建、编辑、复制历史活动、公开路线解析、GPX 导入、报名审批、集合方式分仓、后援车基础信息、活动内临时分组、凭证与通知等能力，但核心模型仍是“个人 + 单体活动”：

- 活动只有 `created_by`，没有长期组织归属；发布后的活动默认面向全平台可见。
- 权限只有全局 `admin/member`，无法表达“某人只管理某个俱乐部”。
- 历史活动可以复制，但没有独立模板、线路库、素材库及版本关系。
- 后援车已有容量、司机和联系方式等基础字段，但补给点、领队/收队、车辆分配和应急流程仍是非结构化信息。
- 设置页目前主要承载更新日志；账号、隐私、通知、外观和数据管理尚未形成设置中心。
- 个人资料已有基础身份和紧急联系人信息，报名时可填写临时骑行经验；体重、FTP、功体比和长期能力档案尚未建模。

因此不建议直接堆叠页面。优先顺序应是：**先建立组织与权限边界，再建设可复用活动资产，随后完善精品局调度，最后叠加能力评估和个性化推荐。**

## 2. 产品原则与关键不变量

1. **俱乐部是长期组织，活动小队是单次活动结构**：两者必须使用不同实体，不能复用 `team_id` 充当俱乐部。
2. **一名用户可加入多个俱乐部，但不设主俱乐部/首选俱乐部**：成员关系独立建模，不在个人资料中保存单一 `club_id`；个人中心只展示有效关系，多俱乐部最多展示 4 个头像，超出显示 `+N`。
3. **一个活动最多一个俱乐部**：`club_id` 只能为空或指向一个俱乐部；为空时统一展示“此里公开活动”。本路线图不做联合主办、协办或多个俱乐部共同归属。
4. **权限按俱乐部隔离**：俱乐部管理员只能管理所属俱乐部资源；全局管理员保留审计和应急处置能力。
5. **可见与可报名分开**：活动可以公开展示但仅成员报名，也可以仅成员可见；不可用一个布尔值混合表达。
6. **模板不等于活动副本**：模板是可版本化的复用资产，套用后生成独立草稿，后续修改不得反向污染历史活动或模板。
7. **精品局不是付费标签**：它代表更高组织保障等级，必须绑定人员、车辆、补给和应急预案等可验收能力。
8. **敏感能力数据默认私密**：体重、FTP、功体比用于用户本人评估；向领队或俱乐部开放必须获得用户明确授权。
9. **Strava 始终可选**：路线创建优先使用公开路线解析或 GPX；个人能力数据允许手动录入，不能因 Strava 授权额度阻断主流程。
10. **展示按页面用途取数**：活动列表/详情使用当前俱乐部资料并在不可用时回退发布快照；行程/凭证固定使用发布/成行快照。用户退会、俱乐部停用或关闭后，历史记录继续显示并标注“历史归属”；兼容数据缺少组织身份时中性兜底为“此里公开活动”。

## 3. 目标业务闭环

### 3.1 多俱乐部管理

#### 用户旅程

1. 用户创建俱乐部，填写名称、简介、封面、所在城市、加入方式和默认活动策略。
2. 平台生成俱乐部所有者关系；所有者可邀请管理员、审核成员和配置角色权限。
3. 用户通过公开主页、邀请码或管理员邀请加入俱乐部；同一用户可同时属于多个俱乐部。
4. 发起活动时先选择所属俱乐部，再选择展示范围与报名范围。
5. 用户首页按“全部 / 我的俱乐部 / 公开活动”聚合活动，也可按俱乐部分组订阅与静音。
6. 离开俱乐部后失去私域活动访问权，但其历史报名凭证和必要审计记录按合规周期保留。

#### 角色建议

| 角色 | 核心权限 |
| --- | --- |
| `PLATFORM_OWNER` | 审批俱乐部创建与公开活动、全局风控、停用与兜底处置 |
| `OWNER` | 俱乐部资料、管理员、权限策略、活动审批、移交所有权、解散申请 |
| `ADMIN` | 成员审核、所属俱乐部活动审批、模板与素材管理、通知发布 |
| `ORGANIZER` | 创建和维护本人或被授权的活动、处理报名与分组 |
| `MEMBER` | 查看成员域内容、报名、接收俱乐部通知 |

俱乐部申请和活动发布的详细审批状态机、权限矩阵与边界规则见 [组织地基与审批权限需求](2026-10-17-org-foundation-approval.md)。

权限必须服务端校验，客户端只负责展示。建议使用权限集合而非在代码中到处判断角色名称，为后续自定义角色留接口。

#### 活动可见性矩阵

| 展示范围 `visibility` | 报名范围 `join_policy` | 行为 |
| --- | --- | --- |
| `PUBLIC` | `PUBLIC` | 所有人可见、符合条件即可报名 |
| `PUBLIC` | `MEMBERS_ONLY` | 公开展示，非成员可浏览但需先加入俱乐部 |
| `MEMBERS_ONLY` | `MEMBERS_ONLY` | 仅俱乐部成员可查询、查看和报名 |
| `UNLISTED` | `INVITE_ONLY` | 不进入列表，仅持有效邀请的用户可访问 |

首期不建议建设独立 Web 管理后台，先在小程序内完成俱乐部主页、成员管理和活动管理闭环，避免维护两套权限和交互。

### 3.2 常用活动资产与快速发布

将“复制历史活动”升级为四层资产，避免一个大模板承载所有内容：

- **线路库**：路线名称、公开路线地址/GPX、里程、爬升、预计时间、难度、轮廓图、集合城市。
- **活动模板**：标题规则、简介、日程、报名字段、人数、装备、费用、风险提示和默认可见范围。
- **素材库**：封面、海报底图、品牌角标、装备清单、注意事项片段；标记版权来源和所属俱乐部。
- **发布草稿**：选择线路与模板后生成活动快照，再填写日期、集合点、领队、名额和临时说明。

#### 快速发布流程

1. 选择俱乐部和“日常活动 / 精品局”。
2. 选择常骑线路，自动填充距离、爬升、预计时间、难度与预览图。
3. 套用活动模板，填充文案、装备、费用、报名项和默认策略。
4. 只修改本次变量：日期、天气提示、集合点、负责人、容量和补给。
5. 发布前显示差异预览和缺项检查；发布后保存来源 `template_id/template_version/route_id` 便于追溯。
6. 活动结束后可选择“用本次活动更新模板”，必须创建新版本，不能静默覆盖。

保留现有“复制历史活动”作为轻量入口；它生成普通草稿，不自动进入公共模板库，也不默认复制含个人信息的司机、电话和报名数据。

### 3.3 精品局与后援车管理

活动增加明确类型：`DAILY`（日常活动）与 `SUPPORTED`（有组织保障的精品局）。精品局开启专属配置，但不影响日常活动的简洁发布流程。

#### 精品局发布硬门槛

- 至少一名总领队和一名收队；分组后每组必须有领队。
- 后援车包含车辆、司机、联系电话、载客/载车容量和服务时段；联系方式仅向已通过报名者按需展示。
- 至少配置集合点、关键补给点、撤离点和结束点。
- 配置天气/取消规则、事故处理、失联处理、保险提示和紧急联系人。
- 发布前通过“保障清单”校验；缺少硬门槛只能保存草稿，不能标记为精品局发布。

#### 执行闭环

1. 报名时选择自行前往或后援车，并填写能力自评与特殊需求。
2. 审批后按能力、同行关系和车辆容量编组；支持手动调整并记录变更人。
3. 为每组指派领队、收队和对应后援车，向参与者发出分组变更通知。
4. 凭证页展示本人小队、集合点、领队和必要联络方式；禁止公开整个通讯录。
5. 活动中记录签到、退出、上车、补给点到达和异常事件。
6. 活动后形成保障复盘：容量使用、退出原因、异常、物资消耗和模板改进项。

### 3.4 设置中心

设置页从“更新日志页”升级为设置中心，更新日志保留为二级入口：

| 分组 | 能力 | 优先级 |
| --- | --- | --- |
| 账号与安全 | 微信资料同步、手机号状态、注销账号、异常登录说明 | P0 |
| 隐私 | 骑行名片可见范围、俱乐部资料可见范围、能力数据授权、黑名单 | P0 |
| 通知 | 报名结果、活动变更、俱乐部新活动、管理员待办；按俱乐部订阅/静音 | P0 |
| 外观与体验 | 跟随系统/浅色/深色、字体与地图偏好 | P1 |
| 路线与连接 | GPX 默认行为、Strava 可选绑定/解绑及额度说明 | P1 |
| 数据管理 | 缓存清理、我的数据导出、账号注销进度 | P1 |
| 帮助与关于 | 隐私协议、用户协议、问题反馈、版本号、更新日志 | P0 |

通知偏好必须在消息入队前由服务端执行，不能只在客户端隐藏；紧急安全通知与普通运营通知要分级。

### 3.5 个人能力档案

#### 数据建议

- 基础录入：`weight_kg`、`ftp_watts`、`metrics_updated_at`、数据来源 `manual/strava/imported`。
- 派生数据：`watts_per_kg = ftp_watts / weight_kg`，由服务端或客户端即时计算，不作为用户可任意编辑字段。
- 历史快照：体重和 FTP 会变化，使用独立 `athlete_metric_snapshots` 保存时间序列；个人资料只保存最新摘要或引用。
- 可信度：区分“自填”“平台测试”“第三方同步”，不可把自填数据展示为认证结果。

#### 使用边界

- 默认仅本人可见；用户可单独授权某俱乐部的活动组织者在报名审核期查看“能力分层”，而非原始体重。
- 领队侧优先展示活动适配结论与风险提示，例如“预计强度偏高”，避免无必要暴露体重和 FTP。
- 用户可随时撤销授权；已生成的审核快照按活动安全与审计周期保留，规则需在授权时说明。
- 不把功体比作为报名的唯一淘汰标准，应结合历史完成度、自评、路线难度和组织者人工判断。

建议首期采用可解释规则而非黑盒评分：路线距离、爬升、预估时长与用户自评/近期活动完成情况共同给出“轻松 / 合适 / 挑战 / 不建议”四档提示。

### 3.6 报名名单同步到腾讯文档

管理员可将单场活动的报名名单按需同步到本人授权的腾讯文档在线表格，用于线下组织、分组和物资准备。该能力属于外部数据共享，必须晚于管理员权限边界稳定后实施，并遵循以下顺序：

1. 先完成腾讯文档应用主体、V3 表格写入、权限 scope、配额与安全条款的 M0 接入验证。
2. M1 只提供“单活动、管理员手动确认、无敏感字段”的一次性同步；报名与审批主链路不得同步调用外部 API。
3. 真实姓名、手机号默认关闭，只有具备业务必要性、报名者已获明确告知且管理员二次确认时才可进入后续受控阶段；紧急联系人永不导出。
4. 同步任务复用服务端管理员鉴权与异步 Outbox 思路，使用幂等键、重试、状态回执和审计；腾讯侧故障只影响本次同步，不影响报名与审批。
5. 自动增量同步属于 M3 可选能力，必须在撤权、删除、部分成功、限流和费用边界全部验证后单独评审。

完整字段分级、授权旅程、状态机、接口草案和验收标准见 [报名信息同步腾讯文档需求](2026-10-17-tencent-docs-registration-sync.md)。

## 4. 建议数据模型

以下只定义方向，实施前必须同步更新 `docs/cloudbase-schema.md` 并补齐索引、迁移和 ACL 方案。

| 集合 | 关键字段 | 说明 |
| --- | --- | --- |
| `clubs` | `name, slug, owner_openid, join_policy, status` | 俱乐部主体；公开响应不得返回 owner 原始身份标识 |
| `club_members` | `club_id, openid, role, status, joined_at` | 多对多成员关系；`club_id + openid` 唯一 |
| `club_invites` | `club_id, code_hash, role, expires_at, usage_limit` | 邀请码只存摘要并限制次数和有效期 |
| `activity_templates` | `club_id, version, content, status` | 模板版本不可变；发布新版本代替原地覆盖 |
| `route_assets` | `club_id, route_snapshot, source, visibility` | 路线与派生指标，保留来源和更新时间 |
| `media_assets` | `club_id, owner_openid, type, file_ref, status` | 复用现有 owner-bound 上传与 canonical 媒体安全链路 |
| `support_plans` | `activity_id, vehicles, checkpoints, supplies, emergency_plan` | 精品局保障计划，与普通活动主体解耦 |
| `activity_assignments` | `activity_id, registration_id, team_id, role, vehicle_id` | 分组、领队/收队及车辆分配关系 |
| `athlete_metric_snapshots` | `openid, weight_cipher, ftp_watts, source, measured_at` | 敏感指标按时间保存，体重加密，读取需授权 |
| `notification_preferences` | `openid, club_id, event_types, muted_until` | 支持全局与俱乐部级偏好覆盖 |

活动主体建议新增：`club_id`、`activity_type`、`visibility`、`join_policy`、`template_id`、`template_version`、`route_asset_id`。迁移期间允许历史活动 `club_id` 为空，统一归入“历史公开活动”，不得自动猜测俱乐部归属。

## 5. 分阶段路线图

### P0：组织与合规地基

- 俱乐部创建申请统一由平台所有者审批；俱乐部通过后再开放加入/退出、邀请与成员列表。
- `PLATFORM_OWNER/OWNER/ADMIN/ORGANIZER/MEMBER` 权限和跨俱乐部越权测试。
- 普通成员自发活动挂靠俱乐部时由所属俱乐部管理员审批；俱乐部 `OWNER/ADMIN` 的本人活动默认发布并留审计；进入公开活动池时由平台所有者审批。
- 活动挂靠俱乐部；公开、成员可见、邀请访问和报名范围分离。
- 设置中心首版：账号注销、隐私、通知、协议与更新日志入口。
- 发起人资格申请/审批，替代全平台隐式发起权限。
- 数据迁移、审批待办、通知、审计日志、滥用举报和俱乐部停用流程。

**P0 验收**：未经平台所有者审批不能创建正式俱乐部；普通成员的俱乐部活动和普通用户的公开活动未经对应审批不能发布，俱乐部 `OWNER/ADMIN` 本人活动只能在所属有效俱乐部默认发布并留下可追溯审计；A 俱乐部管理员无法读取或修改 B 俱乐部私域资源，非成员无法通过列表、详情、分享或报名接口旁路访问成员活动。

### P1：高频发布与精品局闭环

- 线路库、活动模板、素材库和模板版本管理。
- “线路 + 模板 + 本次变量”的快速发布流程及发布前缺项检查。
- 日常活动/精品局显式类型。
- 车辆、司机、容量、补给点、撤离点、领队/收队和应急预案。
- 审批后手动分组、车辆分配、变更通知和参与者凭证展示。
- 按俱乐部订阅、静音和管理员待办。
- 报名名单腾讯文档同步：先完成 M0 接入验证，再交付无敏感字段的单活动手动同步；自动增量同步不进入本阶段。

**P1 验收**：组织者能在不重新录入稳定资料的情况下，从常骑线路创建草稿；精品局缺少保障硬门槛时不能发布，分组变更可追溯且只通知受影响用户；腾讯文档能力只有在官方 V3 接口、scope、配额和撤权行为实测通过后才进入 M1，外部同步失败不得影响报名审批主链路。

### P2：个人能力与活动适配

- 体重、FTP、功体比及历史快照；手动录入优先，第三方同步可选。
- 能力数据授权、撤销、加密、审计和数据导出。
- 结合路线和近期完成情况的可解释适配提示。
- 个人骑行统计、活动完成记录和能力趋势。
- 活动搜索与受控标签：新手友好、爬坡、耐力、亲子、精品局等。

**P2 验收**：未授权的组织者只能看到报名所需的适配结论，不能获得原始体重、FTP 或功体比；删除或撤销后按既定合规策略生效。

### P3：规模化运营

- 俱乐部运营看板：活跃成员、活动转化、爽约、容量和路线热度。
- 候补自动递补、取消策略、费用/押金（需单独支付与退款设计）。
- 团队报名与同一俱乐部内的多人协作；联合主办、协办和跨俱乐部共同归属不纳入路线图。
- 山区离线路线、应急定位分享与弱网签到。
- 独立 Web 管理后台，在权限模型稳定后复用同一服务端策略。

## 6. 额外必要升级清单

除用户提出的五类能力外，建议同步纳入：

1. **安全治理**：举报、拉黑、俱乐部停用、管理员操作审计、敏感信息访问审计。
2. **活动可靠性**：候补、取消/改期通知、天气预警、报名截止和爽约记录。
3. **发起人治理**：资格申请、历史完成率、违规处置和权限撤回。
4. **发现与筛选**：按城市、日期、距离、爬升、难度、俱乐部和活动类型筛选。
5. **数据可携带性**：个人资料、报名历史和路线数据导出；账号注销与保留期说明。
6. **无障碍与弱网**：大字号、重要颜色不作为唯一信号、离线凭证与关键联系人缓存。
7. **可观测性**：发布、报名、审批、通知、分组和签到的端到端成功率与失败告警。
8. **反滥用**：邀请频率、活动发布频率、批量通知和图片上传限流。

## 7. 实施前置与风险

- **权限改造是最高风险项**：必须先定义服务端授权矩阵、负向契约测试和迁移策略，再做页面。
- **查询与索引**：多俱乐部活动流需要按成员关系分页聚合；避免把所有俱乐部 ID 一次性下发后做超长 `in` 查询。
- **隐私与合规**：体重属于敏感健康相关信息，需最小化采集、加密、授权、撤销和删除机制；日志不得记录原值。
- **联系方式泄露**：司机、领队与紧急联系人只在必要阶段、必要对象中展示，并使用脱敏或临时联系方案。
- **模板媒体生命周期**：模板引用的图片不可随某次活动删除；需建立引用计数或独立资产生命周期。
- **Strava 额度**：当前第三方授权容量不适合成为主流程依赖；自动同步只能作为增强能力。
- **CloudBase 成本与限制**：新增集合、聚合查询、通知和图片流量上线前需做容量与成本评估。
