# 报名与活动信息简化设计

## 背景与目标

当前报名主链已覆盖资料校验、Strava 数据准备、提交、审批、签到和取消，但仍存在以下产品问题：

- 报名凭证展示条形码，管理员审批页提供扫码核销，与实际采用的手工确认签到重复；
- 性别仅保存在个人资料中，报名确认、报名快照和审批页面没有明确展示；
- 活动模型已支持日程和费用明细，活动编辑页却没有维护入口；
- 骑手称号已失去编辑来源，但个人名片、公开骑友卡和管理员能力卡仍在展示历史值；
- 路线操作属于核心能力，后续调整不能削弱现有入口。

本期采用最小闭环改造，不新增集合，不执行批量数据迁移，保持现有报名、审批和路线架构。

## 范围

### 本期包含

- 移除报名凭证条形码及其说明；
- 移除管理员扫码核销入口；
- 保留管理员报名详情中的手工“确认签到”能力；
- 在报名确认、报名凭证和管理员审批中明确标注性别；
- 报名提交时将性别写入报名快照；
- 公开骑友卡展示性别，并按性别使用不同背景；
- 个人骑行名片和管理员骑手能力卡同步采用性别背景；
- 为活动编辑页增加日程、费用包含和费用不包含的编辑能力；
- 移除所有用户可见的骑手称号展示；
- 保留复制 Strava 路线、复制活动链接、保存分享海报、导出 GPX 四类路线操作。

### 本期不包含

- 不删除数据库中历史 `title` 字段；
- 不批量回填历史报名的性别快照；
- 不改变 Strava 授权、报名名额、候补、审批和通知规则；
- 不修改签到状态机或后端 `checkIn` 接口；
- 不重做活动详情、个人中心或活动列表的整体视觉结构。

## 方案决策

采用“报名快照为主、历史资料兼容回退”的方案：

1. 新报名必须有有效性别，并写入 `profile_snapshot.gender`。
2. 报名相关页面优先读取报名快照，确保审核依据与提交时一致。
3. 历史报名缺少快照性别时，管理员能力卡和公开骑友卡可从当前个人资料读取有效性别；仍无法确定时显示“未标注”。
4. 不因历史数据缺失阻断查看、审批或签到。
5. 背景颜色只作为辅助信息，所有卡片始终显示“性别 男 / 女 / 未标注”文字，不能只靠颜色表达。

## 性别数据与展示

### 数据规则

- 有效值限定为 `男`、`女`。
- 个人资料编辑页继续作为性别的唯一维护入口。
- 客户端报名校验和服务端 `assertProfileReady` 都必须检查性别，避免绕过客户端提交缺失或非法值。
- 报名提交将规范化后的性别写入 `profile_snapshot.gender`。
- 用户自己的报名响应、管理员审批响应和公开骑友投影只返回规范化性别；非法值统一降级为空值。
- 公开骑友响应新增性别属于有意扩展的公开字段。实名、电话、紧急联系人、openid 和原始资料对象仍不得进入公开响应。

### 页面展示

- 报名确认页：实名信息区增加只读“性别”行，并保留“完善资料”入口。
- 报名凭证：骑手姓名下方增加“性别”行。
- 管理员审批列表：骑手摘要中显示性别，便于快速区分。
- 管理员审批详情：能力卡和报名快照均显示性别。
- 活动详情公开骑友卡：姓名附近显示性别标签。
- 个人骑行名片：身份区显示性别标签。

### 骑行卡片背景

卡片使用三种稳定视觉状态：

- `男`：冷灰主背景配蓝绿色强调色；
- `女`：暖灰主背景配珊瑚红强调色；
- `未标注`：现有中性深灰背景配品牌橙强调色。

该规则应用于个人骑行名片、活动详情公开骑友卡和管理员骑手能力卡。真实骑行照片仍是主视觉；性别背景用于无照片兜底层、信息面板和边缘强调，不对照片施加强烈染色。深色、浅色主题下均需满足文字对比度要求。

## 条形码与签到简化

### 用户端

- 删除报名凭证页的条形码画布、绘制逻辑和“向管理员出示条码”说明。
- 报名凭证继续展示活动、状态、骑手、性别、集合方式、集合地点、日程和取消报名入口。
- 页面名称和导航保持不变，避免影响已有跳转。

### 管理端

- 删除审批列表的“扫码核销”按钮和 `wx.scanCode` 流程。
- 管理员仍从审批列表进入报名详情。
- 只有 `approved` 状态显示“确认签到”；确认弹窗、幂等处理、审计记录和 `checked_in` 状态保持不变。

### 代码清理

- 删除不再被引用的 `miniprogram/utils/check-in-code.ts`。
- 删除条码解析、生成、绘制及扫码页面测试。
- 保留手工签到领域测试和页面交互测试。

## 活动日程编辑

活动编辑页新增“时间安排”区块，使用可增删、可排序保持输入顺序的行式编辑器。

每行字段：

- 时间：必填，最长 20 字；
- 标题：必填，最长 100 字；
- 地点：选填，最长 200 字；
- 备注：选填，最长 500 字。

交互规则：

- 空列表显示“添加日程”；
- 每行提供删除按钮；
- 最多 50 行，与服务端现有约束一致；
- 保存前若存在缺少时间或标题的行，页面阻止提交并定位明确错误；
- 保存时保留用户排列顺序；
- 编辑已有活动时完整回填 `schedule`；
- 活动详情继续按现有时间线组件展示，不改变读取格式。

## 费用明细编辑

活动编辑页在现有“费用说明”附近增加两个多行字段：

- 费用包含：每行一项；
- 费用不包含：每行一项。

保存时按换行拆分、去除首尾空白并过滤空行，分别写入 `feeIncluded` 和 `feeExcluded`。每组最多 50 项，每项最长 200 字，复用服务端现有约束。

费用对象的保存条件为以下任一字段有内容：

- 费用说明；
- 费用包含；
- 费用不包含。

三者均为空时不发送费用对象，保持当前兼容行为。活动详情的费用区升级为同时展示说明、包含和不包含；只有存在内容的分组才渲染。

## 骑手称号清理

- 个人中心身份区不再展示称号；
- 个人骑行名片不再展示称号；
- 活动详情公开骑友卡不再展示称号或“骑行爱好者”兜底文案；
- 管理员能力卡不再读取或展示称号；
- 公开骑友和能力卡投影不再返回 `title`；
- 个人资料模型和数据库中的历史 `title` 暂时保留，作为只读兼容字段，避免扩大迁移范围。

显示名称、头像、性别、报名状态和 Strava 指标保持不变。

## 路线能力不变量

以下操作必须继续存在并保持原有行为：

- 有 Strava 路线 URL 时可复制 Strava 路线；
- 始终可复制活动链接；
- 可生成并保存分享海报；
- 有 Strava 路线 ID 时可导出 GPX。

本期不修改按钮可见条件、分享路径、海报绘制、GPX 大小限制和错误提示。相关静态契约与页面测试必须作为回归门禁。

## 数据流

### 新报名

1. 客户端加载个人资料并只读展示性别。
2. 客户端校验性别、实名、电话、紧急联系人、集合方式和 Strava 状态。
3. 服务端重新校验资料完整性及性别合法性。
4. 服务端把规范化性别写入 `profile_snapshot.gender`。
5. 用户凭证和管理员审批从快照读取性别。
6. 活动公开骑友投影返回经过白名单过滤的性别。

### 历史报名

1. 若 `profile_snapshot.gender` 为有效值，直接使用；
2. 管理员或公开骑友读取已经加载当前资料时，可回退到当前资料中的有效性别；
3. 其余场景显示“未标注”，使用中性卡片背景；
4. 不回写历史报名，不因缺失性别拒绝历史审批或签到。

## 错误处理

- 性别缺失或非法的新报名在客户端显示“请先在个人资料中选择性别”，服务端返回 `PROFILE_INCOMPLETE`。
- 日程行不完整时不发起保存请求，并显示具体行号和缺失字段。
- 超过服务端数量或长度限制时由客户端提前阻止；服务端校验仍作为最终边界。
- 卡片无法识别性别时使用“未标注”和中性背景，不抛出页面错误。
- 日程、费用或性别读取失败不得影响路线操作和历史报名查看。

## 测试策略

### 领域与映射测试

- 资料性别为 `男`、`女`时允许报名并写入快照；
- 性别缺失、空白或非法时服务端拒绝报名；
- 报名响应、管理员响应和公开骑友响应只返回合法性别；
- 历史快照缺失时按当前资料回退，均缺失时返回未标注状态；
- 公开骑友响应不包含称号或任何新增敏感字段；
- 日程和费用明细的清洗、长度、数量和回填保持正确。

### 页面测试

- 报名确认、凭证、审批列表和审批详情正确显示性别；
- 三类骑行卡片生成正确的性别样式类并保留文字标签；
- 凭证页不存在条形码画布和说明；
- 审批列表不存在扫码入口；
- 管理员仍可在详情页完成手工签到；
- 日程可添加、删除、编辑、回填并阻止不完整行保存；
- 费用包含和不包含可回填并按行保存；
- 所有称号展示入口消失。

### 回归门禁

- 复制 Strava 路线、复制活动链接、保存分享海报、导出 GPX 四类入口全部存在；
- 报名、候补、审批、驳回、取消和手工签到状态流转通过；
- 执行 `npm run validate`，通过前端测试、云函数测试、安全契约、类型检查和构建验证。

## 发布与兼容

- 不需要数据库迁移；
- 涉及报名快照与审批投影的云函数按现有共享领域代码同步发布；
- 先部署服务端兼容读取，再上传小程序版本；
- 发布后以一条新报名和一条历史报名分别验证性别展示；
- 最终验证活动详情四类路线操作和管理员手工签到。

## 验收标准

- 新报名没有有效性别时无法提交，已有有效性别只读带入；
- 新报名的性别进入快照，并在用户凭证和管理员审批中明确标注；
- 活动公开骑友卡显示性别标签及对应背景，未知性别有中性降级；
- 个人、公开和管理员骑行卡片均不再显示称号；
- 用户端无条形码，管理端无扫码入口，手工签到仍可用；
- 管理员可完整维护活动日程、费用包含和费用不包含；
- 活动详情继续完整提供四类路线操作；
- 全量验证门禁通过。
