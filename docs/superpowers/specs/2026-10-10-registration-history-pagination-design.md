# 我的行程历史保留与分页设计

## 背景

`HP-20261009-07` 要求“我的行程”永久保留历史、已完成、下架和活动实体缺失的报名记录。当前实现存在两个直接缺口：

- `registration/mine` 固定读取 50 条，没有分页，超过 50 条的报名会静默消失。
- 页面同时等待 `listRegistrations()` 和公开活动列表；公开列表失败会拖垮整页，而服务端已经为每条报名返回 owner-bound 活动投影。

PR #48 已提供活动投影与快照降级基础，本设计只补齐稳定分页、异常隔离和明确展示语义。

## 目标

1. 101 条及更多报名可完整读取，顺序稳定、无重复、无遗漏。
2. 已完成、`draft` 下架、软删和物理缺失活动都可解释展示。
3. “我的行程”不依赖公开活动列表成功。
4. 保持旧客户端 `mine` 数组协议可用，避免云函数先部署时破坏现有开发版。
5. 所有响应继续执行报名与活动白名单投影，不暴露 `openid`、内部备注或删除元数据。

## 非目标

- 不改变报名状态机、正常活动的取消/重新报名规则或容量逻辑。
- 不在本轮增加无限滚动 UI；仓储层透明读取全部报名，页面继续一次性展示。
- 不迁移或删除历史报名和活动数据。
- 不用公开活动列表补齐报名活动信息。

## 方案选择

### 采用：兼容式 `minePage` + 仓储层透明聚合

新增 `registration/minePage`，返回严格分页 envelope：

```json
{
  "items": [],
  "next_cursor": "opaque-or-null"
}
```

客户端 `listRegistrations()` 保持原有 `Promise<Registration[]>` 接口，在仓储层循环调用 `minePage`，直到 `next_cursor` 为 `null`。旧 `mine` 动作保留原有数组响应，供已上传但尚未更新的客户端继续使用。

优点：

- 云函数与客户端可分阶段部署。
- 现有页面及其他调用方无需理解分页协议。
- 分页协议可单独严格校验，异常响应 fail closed。

### 不采用：直接扩大 `mine` 的 limit

一次性扩大上限仍会在未来再次截断，并增加单次响应体和活动回查压力。

### 不采用：页面逐页加载并显示“加载更多”

这会扩大 UI、交互和状态机范围，而用户目标是永久保留全部行程。当前数据规模下由仓储层透明聚合更小、更一致。

## 服务端设计

### 分页顺序

报名按以下复合键降序：

1. `created_at DESC`
2. `_id DESC`

游标包含版本、规范 ISO 时间和最后一条 `_id`，使用 base64url 编码。服务端拒绝：

- 非 base64url、超长或无法往返编码的游标；
- 未知版本、缺字段或多余字段；
- 非规范 ISO 时间；
- 空或超长 `_id`；
- 非整数、超范围 `page_size`。

`page_size` 上限为 50。查询读取 `page_size + 1` 条来判断是否有下一页，不使用 `skip`。同时间戳记录用 `_id` 作为确定性边界。

### 索引

新增复合索引：

```text
registrations_openid_created_at_id
openid ASC, created_at DESC, _id DESC
```

保留原 `registrations_openid_created_at`，避免未确认 CloudBase 索引替换行为导致现有查询中断。

### 活动投影

每页只回查该页报名涉及的活动 ID，并按 20 条分批。每条报名返回：

- 活动实体正常：使用实体中的 owner-bound 投影；
- `draft` 或 `is_deleted=true`：保留实体题名和时间，但输出为不可报名的 `finished` 历史活动；
- 活动实体缺失：优先使用报名 `activity_snapshot`；
- 实体和快照都不完整：题名为“历史活动”，时间回退到报名创建时间。

降级输出继续经过 `publicActivity`，因此包含稳定的 `registration_state=closed` 和可解释的关闭原因，不透传 `is_deleted`、`created_by` 等内部字段。

### 缺失活动的取消合同

活动实体被物理删除后，报名仍属于本人且必须可收敛到 `cancelled`：

- `waiting` 报名沿用现有逻辑，直接取消；
- 其他可取消状态在活动实体缺失时更新报名、写审计，但不回写已不存在的名额和候补队列；
- 活动实体仍存在但名额计数畸形时继续 fail closed，不能借降级路径掩盖数据损坏；
- 正常活动继续在同一事务释放名额并提升候补，原有原子性不变。

## 客户端设计

### 仓储层

新增私有分页映射，严格要求 envelope 只包含 `items` 和 `next_cursor`：

- `items` 必须为对象数组；
- `next_cursor` 必须为 `null` 或长度 1 至 512 的字符串；
- 下一页游标不得与当前游标重复；
- 最多读取 200 页，防止异常服务端造成无限循环；
- 跨页按报名 ID 防重；发现重复 ID 时视为响应异常，不静默吞掉。

`MockRepository.listRegistrations()` 保持原行为，不引入无意义的模拟分页。

### 页面

页面只调用 `rideService.listRegistrations()`。活动显示顺序：

1. 服务端报名活动投影；
2. 本地兜底“历史活动”。

移除 `listActivities()` 请求后，公开活动接口故障不再影响“我的行程”。现有 request generation、旧数据刷新和非阻塞错误行为保持不变。

## 错误处理

- 非法分页请求返回稳定 `VALIDATION_FAILED`。
- 数据库或活动回查失败返回通用服务端错误，不输出底层查询信息。
- 客户端分页 envelope、游标或重复 ID 异常统一抛出 `INVALID_RESPONSE`。
- 首次加载失败显示阻塞错误；已有数据刷新失败继续保留旧数据并显示非阻塞错误。

## 测试与证据

### RED/GREEN 自动化

1. 服务端 101 条按 `50 + 50 + 1` 返回，顺序稳定且无漏重。
2. 101 条相同 `created_at` 时按 `_id DESC` 跨页。
3. 非法 `page_size` 和游标在读取数据库前失败。
4. `published`、`finished`、`draft`、软删和物理缺失活动均输出安全投影。
5. 活动物理缺失时本人仍可取消报名并写审计；正常活动名额与候补回归不变。
6. 客户端仓储层读取三页并聚合为数组，拒绝重复游标、重复 ID 和异常 envelope。
7. 页面不再调用 `listActivities()`；即使该 mock 配置为失败也不影响行程加载。
8. 现有刷新竞态、后台刷新和历史投影回归保持通过。
