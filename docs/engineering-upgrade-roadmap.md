# 此里项目工程升级清单与实施路线

> 适用仓库：`MengEn-Ink/cili-cycling-miniapp`
>
> 范围：仅提升工程质量、交付安全与研发效率，不新增业务功能。
>
> 原则：复用现有 Harness、affected CI、CloudBase 与微信发布链路；先观测、后告警、再阻断；所有门禁均可独立回滚。

## 1. 目标与成功标准

本路线用于把已有工程能力收敛为可度量、可追踪、可回滚的长期机制：

- PR 在合理时长内得到与影响面匹配的反馈，`main` 始终可发布。
- CloudBase 与微信开发版只部署真实受影响的产物，发布过程可审计、可恢复。
- 关键模块覆盖率、依赖风险、日志隐私和性能预算有明确门槛。
- 文档、验收证据与代码同步演进，不以“单测通过”替代真机或生产验收。
- 本地与 CI 使用一致的 Node、依赖锁文件、构建及治理入口。

建议季度级指标：PR 必需检查成功率、P50/P95 耗时、主干红灯恢复时间、发布失败率、回滚耗时、增量覆盖率、依赖漏洞存量、真机验收证据新鲜度。

## 2. 现状基线

以下为仓库当前已有能力，应优先复用而非另建体系：

- 原生微信小程序（TypeScript/WXML/WXSS）与 CloudBase 云函数；CI 使用 Node.js 24，云函数运行时为 `Nodejs20.19`。
- `npm run validate` 已聚合格式、Lint、类型、单测、CI 契约、部署脚本、发布说明、UI 同步、治理、云函数包与构建检查。
- PR 使用 affected Harness；`main` 分别运行 validate、coverage、audit；每日还有全量审计。
- 文档变更已有 docs 模式；CloudBase 与微信上传均通过决策脚本按影响面跳过或执行。
- CloudBase 发布具备 production Environment、并发控制、部署后状态回读、关键配置对账与 smoke。
- 微信开发版上传具备主干版本校验、临时私钥、上传回执及私钥清理。
- 已有仓库治理检查、Dependabot/Secret scanning/CodeQL 基线说明，以及 `cloud.ts` 行覆盖率 90%、分支覆盖率 85% 的专项门禁。
- 验证文档明确区分自动测试、真机/权限/E2E 和外部证据，未执行项不得推断为通过。

## 3. 分级升级清单

### P0：建立可信且稳定的交付底座（0～2 周）

#### 3.1 CI 分层与必需检查契约

- **措施**：固化 `affected-pr` → 聚合 `validate` 的 required-check 契约；为 docs、app、cloud、global-risk 四类变更建立可测试的计划快照；主干保留 validate/coverage/audit 分层。
- **验收**：每类典型 diff 都有决策测试；聚合检查不会因 job 改名失效；文档变更不触发生产或微信上传。
- **风险与回滚**：误分类可能漏检；先记录计划并告警一周，再阻断。异常时回退到全量 `validate`。

#### 3.2 增量覆盖率与关键路径测试

- **措施**：保留全量覆盖率报告和 `cloud.ts` 专项阈值，新增“变更行覆盖率”报告；首阶段仅评论，稳定后对应用核心、仓储适配层和高风险云函数设门槛。
- **验收**：PR 可见变更行覆盖率及未覆盖行；阈值配置版本化；纯文档变更跳过。
- **风险与回滚**：生成代码或不可测胶水代码造成噪声；提供有理由、有期限的排除清单，必要时退回只报告模式。

#### 3.3 构建一致性与可复现环境

- **措施**：统一 `.nvmrc`/engines、Actions Node 版本和开发文档；所有 CI 使用 `npm ci` 与锁文件；校验云函数运行时兼容性，禁止本地隐式依赖全局包。
- **验收**：干净沙箱可仅凭 README 和锁文件完成 `validate`/`build`；CI 记录 Node/npm 版本与产物摘要。
- **风险与回滚**：Node 24 工具链与 Nodejs20.19 云函数存在语法/API 差异；兼容性检查失败时不升级运行时，仅修正编译目标或依赖。

#### 3.4 依赖供应链和安全审计

- **措施**：把锁文件完整性、`npm audit`、CodeQL、Secret scanning、Dependabot 状态纳入治理清单；高危漏洞按“可利用性+运行范围”分级并设处置 SLA。
- **验收**：新增高危且可利用漏洞阻断合并；审计报告作为 artifact 保存；所有豁免含负责人、原因、到期日。
- **风险与回滚**：上游误报导致阻塞；允许限时豁免，不以无边界的 `audit fix --force` 破坏锁文件。

#### 3.5 CloudBase 与微信发布安全

- **措施**：保持 CI 成功后、按 diff 部署；将 deployment decision、目标环境、提交 SHA、产物摘要、smoke 结果统一写入发布回执；明确失败后的重试和人工回退步骤。
- **验收**：同一 SHA 可追踪到 CI、CloudBase 和微信上传回执；旧流水线不能覆盖新主干；文档/测试变更稳定跳过。
- **风险与回滚**：决策脚本错误可能漏发或多发；高风险变更先采用“决策+人工确认”，异常时手动触发已验证提交的工作流。

#### 3.6 日志、隐私与密钥基线

- **措施**：定义禁止记录字段（token、手机号、openid、精确位置、上传私钥等），提供统一脱敏函数；对 CI artifact、云函数日志和错误堆栈做抽样扫描。
- **验收**：测试覆盖脱敏规则；扫描发现明文敏感信息即阻断；发布私钥仅存在于临时文件且无论成败均清理。
- **风险与回滚**：过度脱敏影响排障；保留不可逆关联 ID，不回退到记录原始隐私数据。

### P1：提升可维护性与验收可信度（2～6 周）

#### 3.7 架构边界与依赖方向

- **措施**：明确页面/组件、应用编排、领域规则、repositories/cloud 适配、云函数之间的依赖方向；用 ESLint 或治理脚本禁止页面直接散落调用云 API、禁止跨层反向依赖。
- **验收**：边界规则有正反例测试；新增调用优先进入统一 repository/service；例外可审计。
- **风险与回滚**：一次性重构风险高；仅约束新增和改动代码，存量按热点逐步收敛。

#### 3.8 配置治理

- **措施**：建立“公开构建配置、GitHub Environment Secret、CloudBase 函数变量、未跟踪本地私有文件”四类清单；为必需项增加启动前校验和部署后对账。
- **验收**：缺配置时快速失败且不打印值；测试、预发、生产边界明确；配置变更有审计记录。
- **风险与回滚**：过严校验阻断非相关流程；按 affected scope 仅检查本次需要的配置。

#### 3.9 E2E、真机与验收证据

- **措施**：按核心旅程维护自动 smoke、微信真机、权限/OAuth、CloudBase 生产 smoke 的验证矩阵；证据包含提交、环境、时间、执行者和结论，并设置有效期。
- **验收**：发布前能区分“自动通过”“人工通过”“未执行”；关键旅程失败可定位到代码与发布回执。
- **风险与回滚**：真机自动化不稳定；先作为发布条件和证据提醒，不用不稳定用例直接阻断普通 PR。

#### 3.10 Pages 与文档治理

- **措施**：延续 docs-only affected 模式；检查 Markdown 相对链接、命令有效性、事实所有者和复核日期；Pages 构建失败不得触发业务部署。
- **验收**：README、运行手册、发布记录、外部证据职责清晰；过期证据可被发现；文档命令可在干净环境复现。
- **风险与回滚**：链接检查受外网波动影响；内部相对链接阻断，外链先重试并告警。

#### 3.11 开发者体验

- **措施**：提供一条快速检查（affected）和一条完整检查（Harness）；统一错误信息输出“失败项、修复命令、报告位置”；缓存只加速、不改变结果。
- **验收**：新开发者可在 30 分钟内完成安装、检查和构建；本地失败与 CI 失败使用相同入口；P95 CI 时长持续可见。
- **风险与回滚**：缓存污染导致幽灵问题；任何缓存均可关闭，并定期执行无缓存全量审计。

### P2：形成数据驱动的持续治理（6～12 周）

#### 3.12 性能与稳定性预算

- **措施**：对主包/分包体积、首屏时间、关键请求耗时、云函数错误率和冷启动建立基线；按页面和函数设置预算，先趋势告警再门禁。
- **验收**：每次主干构建生成趋势报告；超过预算需附解释或优化计划；生产异常可关联提交和函数版本。
- **风险与回滚**：测试环境波动；采用多次采样和趋势判断，单点异常不直接阻断。

#### 3.13 发布与恢复演练

- **措施**：季度演练 CloudBase 单函数回退、微信开发版重新上传、Secret 轮换和错误决策恢复；记录 RTO、步骤与缺口。
- **验收**：演练无需依赖个人记忆；回退对象和数据兼容边界明确；行动项进入清单并按期关闭。
- **风险与回滚**：演练误触生产；默认在隔离环境执行，生产演练需 Environment 审批和明确观察窗口。

#### 3.14 工程健康看板

- **措施**：汇总 CI 时长/成功率、覆盖率、漏洞、发布成功率、回滚耗时、证据新鲜度和包体趋势；只展示可行动指标。
- **验收**：指标有来源、负责人和阈值；月度回顾能产生明确行动，而非仅展示数据。
- **风险与回滚**：指标驱动投机；不以单一数字评价个人，删除长期无行动价值的指标。

## 4. 实施路线

### 第 1～2 周：P0 基线

1. 为 affected 决策补齐四类契约测试，确认 required check 名称稳定。
2. 输出增量覆盖率与 CI 耗时报告，暂不新增阻断。
3. 固化 Node/npm/锁文件和云函数兼容性检查。
4. 补齐供应链豁免模板、日志敏感字段清单和统一发布回执。
5. 在一周观测期后，只启用低误报的高危漏洞、密钥泄漏和关键决策测试阻断。

### 第 3～6 周：P1 收敛

1. 对新增代码启用架构边界规则，按热点迁移存量调用。
2. 建立配置分类清单及 affected 配置校验。
3. 建立核心旅程验收矩阵和证据有效期提醒。
4. 上线 Markdown 相对链接与命令检查，优化 Harness 错误摘要。
5. 根据观测数据确定增量覆盖率阈值，并保留限时豁免机制。

### 第 7～12 周：P2 持续治理

1. 建立包体、页面和云函数性能基线，连续两周观测后启用趋势告警。
2. 完成一次隔离环境恢复演练，修订 CloudBase/微信发布手册。
3. 发布轻量工程健康看板并开展月度回顾。
4. 清理无效门禁、重复脚本和到期豁免，复盘季度指标。

## 5. 执行与变更规则

每个升级项应以独立 PR 落地，并包含：现状证据、目标指标、影响面、测试、发布方式、回滚开关和负责人。门禁默认按以下阶段推进：

1. **观测**：生成报告，不改变合并或发布结果。
2. **告警**：在 PR/主干明确提示，允许带理由继续。
3. **阻断**：仅对低误报且有明确修复路径的问题启用。

涉及 CloudBase、微信上传、Secret 或生产 smoke 的变化，必须通过 GitHub Environment 管理；不得在本地或 CI 日志输出 Secret。任何新增门禁若造成持续误报，可独立降级到告警，不回滚其他已验证能力。

## 6. 完成定义（Definition of Done）

- CI 决策、构建、测试、审计和发布回执可由同一提交 SHA 串联。
- 文档、测试与非产物变更不会误触 CloudBase 或微信开发版部署。
- 新增/修改代码满足分层质量门禁，关键路径不存在无期限覆盖率或安全豁免。
- 生产配置缺失会安全失败，日志及 artifact 不包含明文敏感信息。
- 自动测试、真机验收和生产 smoke 的结论不混用，未执行项明确标注。
- 发布失败有可执行的重试、回退和人工确认路径，并至少完成一次演练。
- 所有工程指标均有负责人、阈值、复核周期和下线条件。
